# Oneliner MVP design

**Status:** Approved for implementation; private-group design clarified and approved on 20 October 2026. The [approved product definition](../../product/oneliner-mvp.md) controls what to build and what counts as done. This document records the implementation design. Task 5 follows the approved MVP plan and the group-design review.

## Purpose and release boundary

Oneliner is a mobile-friendly trading journal for futures traders. A trader can capture a trade in a short natural-language note, finish it later, review the week, and optionally compare summary performance with friends. The first release is small enough to deploy for a handful of testers and useful without a broker connection.

The MVP includes account sign-in, trade capture and completion, a weekly review, and private groups. It does not include broker imports, live execution tracking, order placement, partial fills, scaled positions, fees, automated trade verification, or AI-written performance advice.

## Experience

1. A signed-in trader writes a note such as “CL short 87.64, stop 87.90, opening range breakout.” Oneliner sends the note to an AI parser and shows an editable preview. The parser may suggest symbol, long or short, entry, initial stop, and setup name. It is instructed to return an empty field and a plain-language clarification when a value is absent or ambiguous. Suggestions are never treated as verified values; the user confirms them before saving.
2. The opening time defaults to the current time and can be edited. The user must confirm symbol, direction, entry, initial stop, setup name, and opening time before saving. The initial stop must be on the loss side of entry and cannot equal entry. The original note is saved exactly as entered alongside the confirmed fields.
3. A trade can remain unfinished. The inbox lists the user's trades without an exit. Adding one exit price completes a trade. Oneliner calculates its R result and labels it win, loss, or breakeven. The user can correct a trade's own details or exit later; the calculated result and summaries update accordingly.
4. The review page shows the trades opened in a selected week, their original notes, completed results, total R, win rate, completed count, and unfinished count. An unfinished trade can be completed from this page. It is available throughout the week; “Sunday review” is a use case, not a scheduled job.
5. A user can create a private group and share an invite link. Before joining, a friend sees that joining shares weekly total R, win rate, and completed trade count with group members. Joining is the opt-in. Members can leave; the owner can remove members, regenerate the invite link, or close the group. Removing a member also rotates the invite link so the removed member cannot reuse it. A former member can no longer see the group's data, and the group can no longer see that member's summaries. No member can see another member's notes, individual trades, prices, or setups.

The interface uses four destinations: Capture, Inbox, Review, and Friends. The mobile layout uses bottom navigation; larger screens use a sidebar. The visual direction is dark graphite surfaces, clear off-white type, and restrained amber accents. Green and red communicate results only. The standalone [`public/preview.html`](../../../public/preview.html) is a visual concept with sample data; it is not the functional application.

The mobile reference images supplied on 18 October 2026 sharpen the Review layout: a weekly R headline and completed count appear first, followed by a compact daily status chart, actionable Missing outcomes cards, and the week's trade list. The chart groups trade status by opening day, including unfinished trades. Use generous spacing, rounded graphite cards, restrained borders, readable note text, and a persistent bottom navigation with safe-area clearance. A missing-outcome card has an exit-price action; saving the exit reveals the calculated R and win/loss/breakeven label. Results use text as well as color. The Review is live, so it has no scheduled-build timestamp. The pictured setup leaderboard and “Watch it run” control are visual references only and are outside the approved MVP.

## Result and week rules

The MVP models one entry, one initial stop, and one exit per trade. Prices are stored as decimal values. For a long position, `R = (exit - entry) / (entry - stop)`; for a short position, `R = (entry - exit) / (stop - entry)`. Invalid stops block saving. Positive R is a win, negative R is a loss, and exactly zero is breakeven. The formula uses actual entered exit price but does not account for commissions, contract size changes, or multiple fills.

A week is Monday 00:00 UTC through the next Monday 00:00 UTC, with the end excluded. A trade belongs to the week its position opened, even if its exit is recorded later. Performance totals use completed trades only. Total R sums their unrounded R values and rounds for display. Win rate is wins divided by all completed trades, including breakevens in the denominator. When there are no completed trades, win rate displays as unavailable rather than 0%. Trade count in group comparisons means completed count. Late completions and corrections update the original week's figures. Group figures are labeled self-reported.

## System design

- **Web app and server boundary:** Keep the existing Next.js App Router, TypeScript, and plain CSS scaffold. Capture, Inbox, Review, and Friends are responsive pages. All application reads and writes, including trade and group operations, go through authenticated Next.js route handlers; the browser uses Supabase Auth but does not query journal tables or call business RPCs directly. Routes validate input, derive the signed-in user from the cookie-backed Supabase session, and use a request-scoped Supabase client with that user's identity so row-level security applies. User-specific responses are not cached.
- **Identity and storage:** Supabase Auth provides email one-time-code sign-in with a cookie-backed session available to the Next.js server. Postgres stores `profiles` (user-chosen display name), `trades` (owner, original note, confirmed fields, opening time, optional exit, timestamps, and an idempotency key), `groups`, invite tokens, and `group_members`. Database constraints enforce required fields, positive prices, and valid stop placement. The R result is derived from the stored prices, so corrections update it without a separate editable result field. A unique owner/idempotency-key pair makes capture retries return the same trade instead of creating a duplicate.
- **AI parsing:** An authenticated route handler sends the bounded note to OpenAI using Structured Outputs and returns nullable suggestions and clarification messages without saving a trade. The interface discloses that parsing sends the note to an AI provider. A refusal, timeout, malformed response, or missing key produces a recoverable error and leaves manual entry available. The original note never changes when suggestions are edited.
- **Privacy:** Row-level security restricts individual trade rows to their owner even if a route handler is bypassed or makes an incorrect query. Joining requires a valid invite; other group operations require current membership or ownership, as appropriate. A narrow database aggregate checks current membership and returns only display names, total R, win rate, and completed count for a UTC week. Callable group RPCs live in the exposed `public` schema, fix their search path, verify `auth.uid()` and current membership/ownership, and grant execution only to authenticated users. Internal helpers can live in a private schema. No service-role client is used by application handlers. Invite removal rotates the token. Neither an AI key nor a database service key is exposed to the browser.
- **Deployment:** The Next.js server needs a host that runs route handlers; Vercel is a candidate, not a product requirement. Supabase hosts Auth and Postgres. OpenAI is used only for note extraction. Provider projects and keys are configured at deployment time.

The browser keeps an unsaved form draft in session storage across refreshes in the same tab and clears it after a confirmed save or sign-out. The interface never calls an unsaved draft “saved.” The Save action reports success only after the database confirms the write. A failed save leaves the note and corrections in place with a clear error and retry action. Save is disabled while a request is pending; a stable idempotency key also protects against repeated requests. The confirmed form and server validation are authoritative; AI output is advisory.

## Private groups: approved Task 5 details

Groups share only display name, weekly total R, win rate, and completed count. All current members appear, including those with no results. The comparison uses the same UTC opening-week rules as personal review; results are labeled self-reported. Individual trade rows, notes, chart imports, prices, setups, and unfinished counts stay private.

The Friends page lists the caller's groups and allows creation. A group has one owner and one reusable active invite. Joining requires a signed-in user, a display name, and an explicit opt-in action after the disclosure. A signed-out invite visitor returns to that invite after OTP sign-in. Display names use the existing profile endpoint; email addresses are never used as group labels.

Members may leave. Owners may remove members, rotate the invite, or close the group. Removal and invite rotation occur atomically. Owners close a group rather than leave it without an owner; ownership transfer is outside this release. Closing deletes only group metadata and membership, never journal trades. Requests after leaving, removal, or closure cannot retrieve group summaries. Previously viewed information cannot be recalled from another person's memory or screenshots.

Group operations use authenticated Next.js handlers and narrowly granted database RPCs. RPCs also enforce authorization when called directly; RLS keeps raw trades owner-only. Group-scoped changes lock the group row so joining and removal cannot race around a token rotation. Repeating a join returns the existing membership rather than creating another row. Private responses use `Cache-Control: private, no-store`; clients clear unauthorized group data and refresh when returning to the page.

Errors preserve form input and only show success after confirmed writes. Invalid, rotated, and closed-group invites get a recoverable generic error. Testing covers both direct database access and the browser flow: two accounts, exact summary fields, win/loss/breakeven/unfinished trades, UTC boundaries, failed request recovery, removal, invalidated links, leaving, and group closure.

## Delivery and review checks

The initial delivery is successful when a friend can sign in on a phone, capture and correct a note, finish it later, view a weekly review, join a private group, and see only shared summary figures. Each behavior change starts with a failing check, followed by the smallest implementation that passes it. The full relevant test suite and TypeScript typecheck must be green before reporting a change as working. Database checks cover R formulas, stop constraints, UTC week boundaries, empty weeks, and access attempts by another account. Playwright exercises the user-facing flow with two accounts, including parser failure, failed-write retry, duplicate-save prevention, leaving/removal, and denied access after removal. Any provider-dependent check that cannot run is reported as unverified rather than described as done.

Known first-release limits are self-reported data, one entry and exit per trade, no fee adjustment, and AI suggestions that require user review. The app must show these limits where they affect a user's interpretation of a result.
